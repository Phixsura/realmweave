# Architecture

## Prime directive

> **Do not encode today's experimental game rules as tomorrow's architectural
> constraints.**

The long-term asset is a Rust engine for **graph-native competitive strategy
games**; the Three Realms ruleset is its first flagship game. Everything
below exists to make changing rules and board topology cheap.

## Crate boundaries

```
realmweave-core      board graph, state, moves, rules   (no UI/net/DB/async)
realmweave-bot       baseline AI opponents              (depends: core)
realmweave-protocol  versioned wire messages            (depends: core)
realmweave-server    rooms, WS, clocks, persistence     (depends: core, protocol)
realmweave-client    Bevy renderer + session/transport  (depends: core, bot, protocol)
realmweave-sim       self-play, balance, fairness       (depends: core)
realmweave-cli       gen/validate/play/replay tooling   (depends: core)
realmweave-supplywar archived RTS lab (opt-in feature)  (depends: core)
```

Rules are one module per ruleset (`core/src/rules/`): `classic.rs`,
`weave_sever.rs` (v2+v3), `trinity_y.rs` (flagship), `shared.rs`
(connectivity predicates), with the trait/registry in `mod.rs`. Dead
experiments are deleted, not flag-gated — git history is the museum.

The client is one module per concern (`client/src/`): `menu`, `board_view`,
`hud`, `bots_ui` (vs-AI + exhibition), `netsync`, `replay_ui`; `main.rs`
holds app assembly, shared resources, and the system schedule.

Hard rules:

- `realmweave-core` never depends on UI, networking, databases, or async
  runtimes. It is the single authoritative rules implementation.
- Game legality never reads rendering coordinates. `Node.position` is a
  layout hint only.
- The victory evaluator lives behind the `RuleSet` trait
  (`legal_moves` / `validate_move` / `apply_move` / `evaluate`) and is looked
  up by versioned id (`three-realms-v1`), which is persisted with every game.
  Replacing it must never touch networking or rendering.
- Boards are data (`BoardDefinition` JSON in `boards/`), generated by
  `realmweave-cli gen-board` and validated in CI. Replacing the topology must
  never require rewriting the rules engine or renderer.

## Determinism and replay

- No randomness anywhere in the engine. Simulation seeds live in
  `realmweave-sim` only.
- `GameRecord { config, moves, result }` fully reconstructs any game via
  `Game::replay`. The server persists exactly this (config + ordered events);
  no per-move snapshots.

## Authority model (online)

- The server owns canonical game state and clocks. Clients send *intent*
  (`PlayMove`, `SwapSides`, `Resign`) and mirror committed events.
- Client-side validation exists only for UX (legal-move highlighting); it is
  never trusted.
- Events carry canonical sequence numbers; duplicate/stale client commands
  are rejected; connections are rate-limited.
- Reconnect uses per-seat tokens. The pie-rule swap exchanges seat tokens on
  the server, so seat identity is always derived from the token.

## Client rendering (Bevy, native)

Distribution target is a native desktop client (Steam). Inside the client the
same boundary discipline applies:

- `session.rs` and `net.rs` contain no Bevy types: session state, intent
  handling, transport.
- Bevy systems read the session and emit `PlayerIntent`s. The 3D stacked view
  and the 2D analysis view are two projections over the same data
  (`layout::node_position`); swapping or adding renderers touches nothing
  else.
- Steamworks integration (achievements, invites, overlay) is a future
  extension point in the client only.

## Persistence

SQLite via sqlx (plain SQL schema, PostgreSQL-portable):

- `games(id, ruleset_id, board_id, config_json, created_at, finished_at, result_json)`
- `events(game_id, seq, ply, player, move_json, ts, clock_json)`

Completed games are reconstructible from config + ordered events, exportable
at `GET /api/games/{id}/record`, and replayable with `realmweave-cli replay`.
